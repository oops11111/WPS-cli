## 2. `open_in_wps` — **not confirmed**

Two runs, the workbook open in an ET instance that the object-table probe could see.

- **Write while open:** `VALIDATION_FAILED` and `MUTATION_ROLLBACK_FAILED`. The restore failed with `WinError 5` (access denied), because WPS held the file. `rollback.performed: false`, so `open_in_wps` was not reported. The file kept the rejected value while WPS had it open.
- **After `Close($false)`:** the next write returned `DOCUMENT_IDENTITY_CHANGED`, because the file on disk had already been normalised by the failed write.

Findings:

- With the document open, the automatic undo cannot replace the file. The result is a failed rollback, not a rolled-back write. The message tells the user to restore manually, but `restore-backup` would hit the same lock.
- `open_in_wps: null` on a closed document means the probe call failed. It does not mean "not open". The probe code returns `open_in_wps: false` when no WPS instance is running, so a `null` points to an error in the attach call. The raw output of `open-documents` is needed to find it.
