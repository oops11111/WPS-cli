# Phase 5 计划：首个正式版本与覆盖扩展

状态：**active**（2026-10-14 确认，五项决定均按默认建议）。

## 目标

Phase 4 证明了这套工具在一台 Windows、一个 WPS 版本、两个 Agent 客户端上能完成写入和恢复，也补上了发布流程。Phase 5 要回答三个问题：

1. 所有工具出错时，Agent 都能看到可处理的错误码吗？Phase 4 的真机评测靠运气才发现了三处“错误码没传到 Agent”的缺陷。
2. Agent 能不能完成 4 个写入任务以外的常见工作：读写已打开的文档、HTML 与 Office 互转、Writer 表格、工作表管理？
3. 别人能不能只装发布包、不拉仓库就用起来？

## 输入：Phase 4 留下的缺口

| 缺口 | 出处 |
| --- | --- |
| 三处错误码没传到 Agent 的缺陷都是真机评测才发现的（#55、#56、#60），没有覆盖全部工具的离线检查 | `CHANGELOG.md` 的 Fixed |
| 评测只有 12 个任务，用到 85 个工具里的 6 个（`backup_document`、`restore_backup`、`html_editable`、`spreadsheet_write`、`writer_replace`、`presentation_replace`）；没有记录选错工具的次数 | `docs/AGENT_E2E_EVAL.md`、P4-014 决定 |
| 版本号仍是从未打标签的 0.1.0；只装 wheel 时不能跑回归（清单和配置不在包里） | `docs/RELEASING.md` |
| 兼容矩阵只有一个 WPS 版本；安装检查不是在干净机器上做的 | `docs/PHASE4_PLAN.md` 开头的例外 |
| 153 个文件不符合 `ruff format`（2026-10-14），CI 不检查格式 | 本地 `ruff format --check .` |

## 出口标准

每一条都要有可机器读取的记录（测试、结果 JSON 或提交到仓库的结果文档），只按实测结果判定。

| # | 出口标准 | 怎么算达成 |
| --- | --- | --- |
| F1 | 每个工具的失败都能被 Agent 看到 | 离线测试对 85 个工具逐个构造一次失败调用：处理文档或文件的工具用未登记的文档、不存在的文件，能占用的再加一次被占用的文件；没有这类输入的工具用不合法的参数。检查结果要么是带错误码的工具结果文本，要么是 JSON-RPC 参数错误；不能出现 `MCP_TOOL_EXECUTION_FAILED` 或空的 `errors`。测试进 CI，找到的问题都修掉 |
| F2 | Agent 评测覆盖更多工作 | 新增至少 6 个任务，覆盖已打开文档的读写、HTML 与 Office 互转、Writer 表格、工作表管理、导出 PDF；每个任务写明预期用到的工具，runner 记录预期之外的调用次数。需要 WPS 的任务在 Windows 上各跑 3 次，至少 2 次通过 |
| F3 | 发布首个正式版本 | 按 `docs/RELEASING.md` 定版本号，打标签，GitHub Release 附 wheel 和源码包；在新的虚拟环境里只装这个 wheel，`inspect-env` 和 safe 档回归都通过 |
| F4 | 格式统一 | 全仓库按 `ruff format` 统一一次，CI 检查格式 |

## 已做的决定

2026-10-14 确认，均按默认建议：

| 决定 | 结论 | 依据 |
| --- | --- | --- |
| 首个版本号 | `0.2.0` | 相对 0.1.0 有新功能（`--close-in-wps`、compat 档）和 MCP 行为变化，按版本规则升次版本号 |
| 发布渠道 | 只发 GitHub Release，不发 PyPI | 目标用户在 Windows 上配合 WPS 使用，先保证 Release 可装可用；PyPI 等有外部用户需求再做 |
| 第二个 WPS 版本 | 不作为出口标准；拿到时按 `docs/COMPATIBILITY_MATRIX.md` 补一节 | Phase 4 已确认拿不到；不让整个阶段卡在外部条件上 |
| Claude Desktop 等其他客户端 | 不做 | P4-014 决定：两个已验证客户端都用 stdio，没有新需求 |
| 全仓库格式化的时机 | Phase 5 第一件事，单独一个只改格式的 PR | 153 个文件，越晚做与其他改动冲突越多 |

## 建议顺序

1. 先做 P5-001：趁没有进行中的改动，一次改完格式。
2. 本地任务：P5-002 和 P5-003，P5-004 和 P5-005，P5-007。
3. P5-008 放在本地任务之后，让版本包含这些修复。
4. Windows 任务合到一次上机：P5-006、P5-009。

## 主要风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 失败契约测试找到很多问题 | F1 拖长 | 先统计再分批修；同一类问题（例如某类命令都缺占用检查）用一处修复覆盖 |
| 新评测任务结果不稳定 | F2 通过率波动 | 沿用 3 次取 2 次；失败时保留完整的工具调用记录，先查是不是工具本身的问题 |
| 只装 wheel 时有些回归场景依赖仓库文件 | F3 达不成 | P5-007 先列出 safe 档每个场景用到的文件；需要仓库的场景改为从包内读取或在文档里写明 |
| 格式化与进行中的分支冲突 | 合并麻烦 | 在没有打开的 PR 时做，并且只改格式 |
| 打错标签或发布内容不对 | 用户装到错误的版本 | 发布前在 CI 产物上先做一次 P5-009 的检查；标签由你在确认后打 |
