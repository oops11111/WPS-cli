# Stage 4 inline animation feasibility: XML candidate accepted, exact playback unverified

Base and merge target: `main` `0a65bb1f54f7ec3e788d9f4fb9af50a7800a4669`. Scope is only launch slide 5's `<span class="fade">全渠道开售</span>` inside `10 月 24 日 全渠道开售`. This is an audit PR: no converter, source fixture, threshold or media change. [Stages 4–6 plan](HTML_PPTX_INLINE_ANIMATION_PLAN.md) defines the dependent implementation and final gates.

## Cause and candidate

`_positioned_slide` and the editable fallback search descendants for an animation. On finding the animated span, each appends the containing text shape/paragraph to `timing_xml`; `_target` can emit only a whole-shape target or `p:pRg`, not a character range. The generated launch slide 5 has one shape (`spid=5`) with two text runs, `10 月 24 日 ` (10 characters) and `全渠道开售` (5). Its visibility and fade behaviors both target the entire shape. The converter explicitly warns that an animation on part of a paragraph was applied to the whole paragraph.

The [Microsoft Open XML text-target reference](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.presentation.textelement) permits `p:charRg`; [Microsoft's animation example](https://learn.microsoft.com/en-us/office/open-xml/presentation/working-with-animation) shows it inside `p:spTgt/p:txEl`. [Microsoft's implementation note](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/d0b4598c-f4e1-47ff-91b0-8fb5abb708f3) says PowerPoint requires `end > st` and `end <=` animated text length. The [disposable candidate](../artifacts/html-pptx-inline-stage4-20261122/candidate_manifest.json) changes both slide 5 targets to `p:charRg st="10" end="15"` and supplies an `end="14"` control. Only `ppt/slides/slide5.xml` differs from the accepted PPTX; the entire slide XML before `<p:timing>` has the same SHA-256 before and after. Shape coordinates, paragraph and run text, colour and formatting XML are therefore unchanged.

The range uses a **hypothesis** of UTF-16 code-unit offsets with an exclusive end. The current run is BMP-only, so its Unicode code-point and UTF-16 offsets happen to agree. This does not make a generic rule safe: a non-BMP prefix changes the units; repeated span text needs element/run identity; and `_runs` collapses and trims whitespace before PPTX serialization. The candidate script intentionally rejects changed source text or run segmentation instead of guessing an offset.

## WPS and static results

Two bounded, hidden WPS Presentation 12.8.2.18913 COM probes opened only disposable copies. The first [baseline/candidate record](../artifacts/html-pptx-inline-stage4-20261122/wps_com.json) reads `TextRangeStart=0`, `TextRangeLength=0` on the whole-shape baseline and `10`, `15` on an earlier byte-distinct but XML-equivalent candidate. The final [control/candidate record](../artifacts/html-pptx-inline-stage4-20261122/wps_com_final.json) reads `10`, `14` for the end-14 control and `10`, `15` for the committed end-15 candidate. Each has one fade effect on the same shape/text, 0.5 s delay and 1.2 s duration, with no COM error. This proves WPS opens the packages and exposes the numeric range fields. The observed `TextRangeLength` follows the raw XML `end` value; it must **not** be interpreted as proof that precisely five characters animate on screen.

A bounded [candidate WPS/Edge static check](../artifacts/html-pptx-inline-stage4-20261122/candidate-static/static_report.json) gives the same six launch page scores as Stage3 (`.9865, .9852, .9862, .9822, .9475, .9981`), zero score delta and applicable semantic aspects 1.0. The other six fixed pages' package contents were not changed. This is evidence that the candidate did not regress static layout, text or formatting in this measured case. It does not establish how WPS displays the partial fade during slideshow.

## Decision and handoff

**Stage 4: STOP for exact inline-animation acceptance.** The format offers a plausible character target, WPS COM accepts its fields, and static layout is stable. The character-index contract across Unicode/whitespace and actual WPS partial fade remain unverified; a clean visual capture is still blocked by the pre-existing desktop error dialog documented in [Stage2](HTML_PPTX_STAGE2_STOP.md). This stage did not operate that dialog or retry unbounded UI automation. It also leaves the absent `teaser.mp4` and visible video-object failure untouched.

Stage 5 should not alter the converter until a bounded clean device run shows that the end-15 target animates only `全渠道开售`, the prefix remains visible, and a general offset rule survives non-BMP/repeated-text/whitespace cases. If those conditions remain unavailable, record a Stage5 skip rather than shipping a fixture-specific offset. Stage 6 must still keep the overall HTML→PPTX claim `best-effort` while media or visual playback gates fail.

Verification: 8 targeted tests passed (candidate invariants, UTF-16 counterexample, existing launch PPTX tests and packaging metadata). The WPS COM script parses without error. Ruff check and format check pass for the three new Python files. CI and parent-agent review remain independent merge gates.
